# 7회차 강사용 진행 스크립트

120분 · 휴식 10분 포함 · 기존 로컬 앱 → GitHub → Vercel → 공유 주소

## 수업 전 준비

- 참여자는 새 앱을 만들지 않고 기존 앱 폴더를 준비합니다.
- VS Code·Git 설치, GitHub·Vercel 본인 계정 로그인을 미리 확인합니다.
- 로컬 앱이 실행되는지, .gitignore에서 .env*·node_modules/·.next/·.vercel/를 제외하는지 확인합니다. .env.example에는 가짜 값만 둡니다.
- 시연용 앱과 가짜 환경 변수 예시를 준비합니다. 실제 키를 화면에 띄우지 않습니다.
- 버튼 이름은 영문/한글 및 버전에 따라 다를 수 있습니다. 매 단계 완료 화면을 보고 다음으로 이동합니다.

## 1. 지금 만든 앱 폴더를 열어요 (00:00–00:15)

화면: VS Code

### 읽을 멘트

“오늘은 여러분이 이미 만든 앱을 인터넷에 올리겠습니다. 지금 앱 폴더를 열어주세요. GitHub는 코드 보관함이고, Vercel은 그 코드로 웹 주소를 만들어주는 곳입니다. 먼저 비밀번호가 든 파일을 보관함에 보내지 않도록 확인할게요.”

### 화면 시연 · 한 동작씩 보여주고 기다리기

1. VS Code → File → Open Folder에서 지금까지 만든 앱 폴더를 열어요. 파일을 모두 저장해요.
2. 브라우저에서 기존 localhost 주소를 열고 앱이 작동하는지 확인해요. 실행 방법이 기억나지 않으면 강사와 확인해요.
3. 폴더 맨 위의 .gitignore에 아래 목록을 추가하고 저장해요. 이 파일은 ‘올리지 않을 파일 목록’이에요.

### 완료 확인

“내 앱이 열리고, .gitignore 파일을 저장했어요. 여기까지 되셨으면 손을 들어주세요.”

### 진행 메모

앱 폴더와 .gitignore를 순회 확인하세요. Git 설치와 GitHub·Vercel 로그인을 확인하고, 로컬 실행이 안 되는 참여자는 기존 오류부터 함께 해결합니다.

제외 목록 예시 (.gitignore):

```gitignore
.env*
!.env.example
node_modules/
.next/
.vercel/
```

이미 기록된 비밀 파일은 .gitignore만으로 제거되지 않습니다. 발견하면 업로드를 멈추고 강사와 키 폐기·재발급 및 기록 정리를 진행합니다.

## 2. 버튼으로 GitHub에 올려요 (00:15–00:45)

화면: VS Code → GitHub

### 읽을 멘트

“왼쪽 가지 모양 버튼을 누르세요. 커밋은 내 컴퓨터에 기록하는 버튼입니다. 아직 인터넷에는 올라가지 않았어요. 이제 Publish to GitHub로 보냅니다. 비공개를 선택해도 배포할 수 있어요. 모두 GitHub에서 내 파일이 보이는지 확인해주세요.”

### 화면 시연 · 한 동작씩 보여주고 기다리기

1. VS Code 왼쪽 Source Control(소스 제어 · 가지 모양)을 눌러요. Initialize Repository(리포지토리 초기화)가 보이면 눌러요. 이미 변경 파일 목록이 보이면 그대로 진행해요.
2. Changes(변경 사항)에서 올릴 파일을 확인해요. .env·.env.local·node_modules가 보이면 멈추고 강사에게 알려주세요.
3. Changes 옆 +로 파일을 준비해요. Staged Changes(스테이징된 변경 사항)를 다시 확인한 뒤 메시지에 ‘앱 배포 준비’를 쓰고 Commit(커밋)을 눌러요. 커밋은 내 컴퓨터에 변경 기록을 남기는 일이에요.
4. View → Command Palette(명령 팔레트)를 열어 Publish to GitHub를 검색하고 실행해요. 브라우저 로그인 안내가 나오면 본인 GitHub 계정으로 로그인한 뒤 VS Code로 돌아와요.
5. 저장소 이름을 my-first-app처럼 영문으로 쓰고 Publish to GitHub private repository(비공개)를 선택해요. 업로드가 끝나면 Open on GitHub를 눌러 파일이 보이는지 확인해요.

### 완료 확인

“내 GitHub 저장소에 앱 파일이 보여요. .env 파일은 없어요. 여기까지 되셨으면 손을 들어주세요.”

### 진행 메모

한 동작씩 시연하고 기다리세요. 기존 GitHub 연결이 있다면 새로 만들지 않고 본인 저장소인지 확인한 뒤 … → Push로 올립니다. 이름·이메일 설정 요청은 강사가 본인 정보로 설정하도록 돕습니다. 00:45–00:55는 휴식입니다.

## 3. 방금 올린 저장소를 가져와요 (00:55–01:15)

화면: Vercel

### 읽을 멘트

“이제 장소를 Vercel로 옮깁니다. 새 프로젝트에서 조금 전 GitHub에 올린 저장소를 찾으세요. Import는 이 코드를 가져온다는 뜻이에요. 내 계정과 저장소 이름이 맞는지 함께 확인합시다. 설정 화면에서 다음 단계까지 기다려주세요.”

### 화면 시연 · 한 동작씩 보여주고 기다리기

1. 아래 ‘Vercel 열기’를 눌러 GitHub 계정으로 로그인해요. 대시보드에서는 Add New… → Project로 들어가요.
2. Import Git Repository에서 GitHub를 연결해요. 저장소 목록이 안 보이면 Configure GitHub App에서 내 저장소 접근을 허용해요.
3. 방금 올린 내 계정 / 저장소 이름을 찾고 옆의 Import(가져오기)를 눌러요.
4. Framework Preset이 내 앱에 맞는지 확인해요. Next.js 앱이라면 Next.js예요. Root Directory는 package.json이 있는 폴더로 정해요. 나머지 빌드 설정은 자동값을 사용해요.

### 완료 확인

“내 저장소 이름이 보이는 프로젝트 설정 화면에 도착했어요. 여기까지 되셨으면 손을 들어주세요.”

### 진행 메모

저장소가 안 보이는 참여자는 GitHub 연결 계정과 저장소 접근 권한을 확인하세요. 엉뚱한 저장소를 가져오지 않았는지 확인합니다.

## 4. 필요한 설정을 넣고 Deploy를 눌러요 (01:15–01:40)

화면: Vercel · 프로젝트 설정

### 읽을 멘트

“환경 변수라는 말은 어렵지만 앱에 필요한 설정이라고 생각하시면 됩니다. 예를 들어 DB 연결 주소예요. 이름과 값, 두 칸으로 나누어 넣습니다. 실제 키가 담긴 화면은 공유하지 마세요. 설정을 넣었으면 Deploy를 누르고 Ready를 기다립니다.”

### 화면 시연 · 한 동작씩 보여주고 기다리기

1. DB·로그인·AI API를 쓰는 앱은 내 .env.local(또는 .env)에서 필요한 이름과 값을 확인해요. 설정이 없는 앱은 바로 Deploy로 가요.
2. Import 화면의 Environment Variables를 펼쳐요. Key / Name에는 = 왼쪽 이름을, Value에는 = 오른쪽 값을 넣어요. 값 바깥의 따옴표는 빼고 실제 값 전체를 복사해요.
3. 내 앱이 사용하는 항목을 하나씩 추가하고 Deploy(배포)를 눌러요. 설정 이름과 값은 다른 사람에게 보여주지 않아요.
4. 배포가 끝나고 Ready가 보일 때까지 기다려요. 오류가 나오면 Build Logs의 첫 오류를 강사와 확인해요.

### 완료 확인

“Vercel에 Ready가 표시되고 Visit으로 앱을 열 수 있어요. 여기까지 되셨으면 손을 들어주세요.”

### 진행 메모

시연은 가짜 값으로만 하세요. DB·Clerk·AI를 쓰는 참여자는 필요한 설정을 빠뜨리지 않았는지 본인이 확인하게 합니다. Clerk 등 외부 서비스의 배포 도메인·운영 키 설정도 확인하세요.

가짜 값으로 설명: `DATABASE_URL=내_DB_연결주소` → Name은 `DATABASE_URL`, Value는 `내_DB_연결주소`. 본인 앱에 없는 항목을 추가하지 않습니다. 비밀 키에 `NEXT_PUBLIC_`을 붙이지 않습니다. 이미 배포했다면 Settings → Environment Variables에서 Production(필요하면 Preview)으로 저장하고 Deployments → … → Redeploy를 실행합니다. 외부 로그인 서비스의 배포 도메인·운영 키 설정도 별도로 확인합니다.

## 5. 휴대전화에서 열어보고 한 번 고쳐요 (01:40–02:00)

화면: 브라우저 → VS Code

### 읽을 멘트

“이제 localhost가 아닌 내 앱 주소가 생겼습니다. 휴대전화로 열어볼까요? 제목을 조금 고쳐서 다시 올려봅시다. 저장, 커밋, 푸시 순서입니다. Vercel이 새 버전을 배포하면 같은 앱 주소에서 수정 결과를 확인할 수 있어요.”

### 화면 시연 · 한 동작씩 보여주고 기다리기

1. Visit을 눌러 https://내프로젝트.vercel.app 형태의 주소를 열어요. 휴대전화에서도 같은 주소를 열어봐요.
2. 내 앱의 대표 기능을 직접 사용해요. DB·로그인이 있다면 로그인 → 저장 → 새로고침 후 조회까지 확인해요.
3. VS Code에서 앱 제목 같은 작은 부분을 바꾸고 저장해요. 소스 제어에서 변경 확인 → + → 메시지 입력 → Commit → … → Push 순서로 올려요.
4. Vercel의 Deployments에서 새 배포가 Ready가 되는지 확인해요. 연결된 배포 브랜치(보통 main)에 올린 수정이 반영되면 앱 주소를 다시 열어 확인해요.

### 완료 확인

“휴대전화에서 앱이 열리고, 수정한 내용도 배포됐어요. 여기까지 되셨으면 손을 들어주세요.”

### 진행 메모

각자 앱 주소와 대표 기능 한 가지를 메모하게 하세요. 새 배포의 Ready와 실제 수정 반영을 확인합니다. 접속 시 로그인 안내가 뜨면 배포 보호 설정과 공유 대상의 접근 가능 여부를 함께 확인합니다.

## 막혔을 때 읽을 말

- GitHub 업로드 실패: “내 계정으로 로그인했는지, Git 이름·이메일 설정 안내가 있는지 확인해볼게요. 기존 저장소 연결은 지우지 말고 현재 화면에서 함께 확인해요.”
- Vercel에 저장소 없음: “GitHub에 파일이 올라갔나요? 연결한 계정과 Configure GitHub App의 저장소 접근 권한을 확인합시다.”
- 배포 오류: “설정을 많이 바꾸기 전에 Build Logs의 첫 오류부터 볼게요. 키와 개인정보는 가리고 보여주세요.”
- 로컬에서만 작동: “환경 변수의 이름과 값, Production 적용 여부를 확인하고 다시 배포합시다. 외부 서비스의 배포 도메인과 운영 설정도 확인할게요.”
- 수정 미반영: “저장 다음 Commit과 Push까지 했나요? 연결된 배포 브랜치와 Vercel의 새 Ready 표시를 확인해요.”

## 마무리 멘트

“오늘 내 컴퓨터의 앱을 GitHub에 보관하고 Vercel로 웹 주소를 만들었습니다. 이후에는 저장 → 변경 확인 → 커밋 → 푸시 순서로 올리면 됩니다. 내 앱 주소와 대표 기능 한 가지를 적어두세요. 다음 시간에는 이 주소로 작품을 소개하겠습니다.”
