# 옥천 AI Class · 1회차 수강생 앱 기획과 개발 준비

작성일: 2026년 10월 14일

로컬 실습을 시작할 때는 [수강생별 Codex·Claude Code 개발 시작 프롬프트](lesson-one-local-build-prompts.md)를 사용합니다. 필요한 DB는 SQLite로, 영상 파일은 로컬 업로드·임시 폴더로 구성하는 학생별 복사용 지시문입니다.

## 2. Vercel로 앱을 만들 때 먼저 설명할 것

### 2.1 화면·서버·DB·파일 저장소는 역할이 달라요

| 구성 | 쉬운 설명 | 이 수업에서 맡는 일 |
| --- | --- | --- |
| 브라우저·React 화면 | 사용자가 보고 누르는 공간 | 행사 목록, 캘린더, 입력 폼, 영상 플레이어, AI 결과 표시 |
| Next.js 서버 API | 요청을 확인하고 처리하는 창구 | 입력 검증, 권한 확인, DB 읽기·쓰기, AI API 호출 |
| Vercel | 웹앱을 배포하고 요청을 실행하는 서비스 | GitHub 코드 배포, 웹 주소 제공, 서버 함수 실행 |
| DB | 검색하고 수정할 수 있는 장부 | 행사 날짜, 일정, 작품명, 원고, 사용자별 기록 |
| 파일 저장소 | 원본 파일을 보관하는 창고 | 영상, 이미지, PDF, 업무 첨부파일, PPTX |
| 로그인·권한 | 누구인지와 무엇을 할 수 있는지 확인 | 내 일정·원고 보호, 작가만 영상 등록, 관리자만 행사 수정 |
| AI API | 서버가 호출하는 외부 생성 서비스 | 슬라이드 구성안, 대화문, 문서 요약 생성 |

기본 구조 제안은 **Next.js + Vercel + 관리형 PostgreSQL + 필요할 때 파일 저장소**입니다. PostgreSQL은 Neon 같은 관리형 서비스를 연결할 수 있고, 파일은 Vercel Blob 같은 객체 저장소에 보관할 수 있습니다. DB·파일 저장소는 웹앱 배포와 별도로 연결·설정합니다. [Vercel Storage 공식 안내](https://vercel.com/docs/storage)

```text
사용자 → 브라우저 화면 → Next.js 서버 API
                            ├─ DB: 제목·날짜·내용·소유자·파일 경로
                            ├─ 파일 저장소: 영상·이미지·첨부파일 원본
                            └─ AI API: 필요한 자료와 질문으로 결과 생성
```

### 2.2 파일 시스템과 영구 저장의 차이

프로젝트의 `public/`은 로고·수업 자료 등 코드와 함께 배포하는 정적 파일에 사용합니다. 사용자 업로드를 배포된 프로젝트 폴더에 계속 쌓는 방식으로 설계하지 않습니다. 서버 함수의 로컬 파일은 영구 저장이나 여러 실행 간 공유에 의존하지 않고, 임시 처리 후 보관할 결과는 DB나 파일 저장소로 옮깁니다. 브라우저 메모리도 새로고침하면 사라집니다. `localStorage`는 같은 브라우저의 실습용 기록에 쓸 수 있지만 다른 기기와 공유되지 않습니다.

| 저장할 것 | 적합한 위치 | 예시 |
| --- | --- | --- |
| 변경하지 않는 공개 샘플 | 저장소의 JSON·CSV·정적 파일 | 첫 실습 행사 5개, 로고 |
| 사용자가 추가·수정하는 작은 기록 | DB | 일정, 행사, 작품 설명, 회차 본문 |
| 큰 원본 파일 | 파일 저장소 | MP4, PDF, PNG, PPTX |
| 파일의 설명과 접근 권한 | DB | `owner_id`, `file_key`, `visibility`, `mime_type`, `size_bytes` |
| 잠깐 쓰는 입력값 | 브라우저 상태 | 아직 저장하지 않은 계산기 입력 |

서버 메모리나 로컬 SQLite 파일을 공용 영구 DB로 가정하지 않는 것이 이번 설계의 원칙입니다. 파일 시스템 동작은 선택한 런타임에서 확인합니다. [Vercel 함수 제한과 런타임 안내](https://vercel.com/docs/functions/limitations)

### 2.3 영상과 대용량 파일의 업로드 흐름

영상 전체를 일반 API 요청에 넣기보다 **서버에서 사용자 권한 확인 → 업로드용 토큰 발급 → 브라우저에서 저장소로 직접 업로드 → 서버에서 업로드 결과 확인 → DB에 파일 정보 저장** 순서로 구현합니다. Vercel Blob 공식 문서는 4.5MB보다 큰 파일에 클라이언트 업로드를 안내합니다. 파일 형식·크기 제한과 업로드 권한도 서버에서 확인합니다. [Vercel Blob 클라이언트 업로드](https://vercel.com/docs/vercel-blob/client-upload)

업로드가 성공해도 DB 저장이 실패할 수 있으므로 실패 상태·재시도·남은 파일 정리를 고려합니다. 영상 저장과 영상 편집·인코딩은 다른 기능입니다. 큰 영상 변환이나 긴 분석은 작업 ID를 발급하고 작업 상태를 조회하는 구조로 분리합니다.

### 2.4 공개 파일과 비공개 파일

작품 공개 영상과 업무 문서·미공개 원고는 공개 범위가 다릅니다. 업무 파일과 미공개 원고는 비공개 저장소에 보관하고, 다운로드할 때 소유자 권한을 검사합니다. DB에 파일 주소를 저장했다고 접근 통제가 자동으로 생기지는 않습니다. 공개 파일은 주소를 아는 사람이 볼 수 있는 범위를 먼저 결정해야 합니다. [Vercel Blob 보안 안내](https://vercel.com/docs/vercel-blob/security)

### 2.5 DB에서 수업할 핵심 개념

- **테이블·행·열**: 일정 한 건이 한 행, 제목과 마감일은 각각 열입니다.
- **기본키·연결키**: `id`로 한 기록을 구별하고 `owner_id`, `project_id`로 사용자와 프로젝트를 연결합니다.
- **CRUD**: 생성(Create), 읽기(Read), 수정(Update), 삭제(Delete)를 한 화면에서 실습합니다.
- **검색·정렬**: 날짜 범위 조회, 카테고리 검색, 마감일 순 정렬을 합니다.
- **권한**: 로그인만 확인하지 말고 요청한 기록이 그 사용자의 것인지 검사합니다.
- **마이그레이션·백업**: 표 구조 변경을 기록하고, 삭제·변경 전 복구 방법을 준비합니다.
- **환경 분리**: 연습용 DB와 운영 DB를 나누어 테스트 중 실제 기록을 지우지 않게 합니다.
- **연결 관리**: 요청마다 연결을 무한히 늘리지 않도록 관리형 DB에 맞는 연결 방식과 풀링을 사용합니다.

### 2.6 AI·알림·배포에서 수업할 핵심 개념

- **환경변수**: AI 키와 DB 비밀번호는 서버 환경변수로 보관합니다. 브라우저용 변수에 비밀 값을 넣지 않습니다.
- **AI 역할과 자료**: 모델에 역할·입력·참고 자료·결과 형식을 전달합니다. DB에 저장했다고 AI가 자동으로 기억하지는 않습니다.
- **생성과 검증**: 결과를 수정 가능한 초안으로 보여주고, 날짜·숫자·자료 출처는 별도로 확인합니다.
- **알림의 두 단계**: 마감이 다가왔는지 찾는 예약 작업과 사용자에게 보내는 이메일·푸시 전송 기능을 구분합니다.
- **실행 제한**: 긴 작업은 함수 실행 시간 안에 끝나는지 확인하고, 작업 큐·별도 처리 서비스·상태 조회를 사용합니다. 제한은 요금제와 실행 방식에 따라 확인합니다. [Vercel Functions 제한](https://vercel.com/docs/functions/limitations)
- **예약 실행의 한계**: Hobby Cron은 하루 한 번 실행과 시간 정밀도 제한이 있어 분 단위 마감 알림을 보장하는 용도로 설계하지 않습니다. 일정은 한국 시간으로 보여주고 서버 저장 시간·시간대 변환을 정합니다. [Vercel Cron 요금제별 제한](https://vercel.com/docs/cron-jobs/usage-and-pricing)
- **운영 비용**: AI 호출, DB, 파일 보관, 다운로드 트래픽, 영상 처리 비용을 구분하고 이용 횟수·파일 크기 제한을 둡니다.
- **오류·로그**: 저장 실패와 AI 실패를 표시하고 재시도할 수 있게 합니다. 비밀번호·업무 자료·원고 전문은 로그에 남기지 않습니다.

## 3. 김기택 · 안녕 옥천

**앱 목표:** 옥천 주민이 주말에 참여할 문화·교육 행사를 빠르게 찾는다.

**첫 버전:** 행사 목록과 상세 화면. 행사명·시작/종료 일시·장소·소개·원문 링크를 표시하고, 날짜와 종류로 좁혀본다. 관리자 등록 화면은 목록이 작동한 다음 추가한다.

**준비할 자료:** 직접 확인한 행사 5~10개, 공연·교육·원데이 클래스 분류, 주최 기관, 신청 방법, 출처 URL, 최종 확인일. 자동 수집보다 수동 등록으로 시작해 취소·변경 정보 갱신 방법을 정한다.

**개발에 필요한 것:**

- 화면: 행사 카드, 이번 주말 필터, 행사 상세, 관리자 입력 폼.
- DB 제안: `events(id, title, category, starts_at, ends_at, venue, description, source_url, checked_at, status)`.
- 파일: 포스터가 필요하면 파일 저장소에 보관하고 DB에 파일 경로 저장. 첫 버전은 텍스트만으로 가능.
- 로그인: 조회는 공개, 등록·수정은 관리자만 허용. 지역 정보 공유를 추가하면 작성자·신고·관리 기능 필요.
- AI: 첫 버전에는 필수 아님. 이후 등록된 행사 자료에 근거한 자연어 검색과 요약 추가.

**만드는 순서:** 샘플 JSON으로 목록 → 날짜 필터 → DB 조회 → 관리자 CRUD → 포스터·자연어 검색.

**완료 확인:** 이번 주말에 해당하는 행사만 나오고 상세 화면의 날짜·장소·원문 링크가 자료와 일치한다. 행사 없음과 취소 상태도 표시한다.

**강의 포인트:** 날짜 데이터, 필터, 출처·갱신일, 읽기 전용 파일에서 DB로 전환.

## 4. 김승애 · GAEMEJAE

**앱 목표:** 작가가 작품 제작 영상을 정리하고 관람객에게 공유한다.

**첫 버전:** 작가가 영상 1개를 업로드하고 작품명·설명·카테고리를 등록한다. 관람객은 갤러리에서 선택해 재생하고 공개 작품 링크를 공유한다. 영상 편집과 음악 합성은 이후 단계로 둔다.

**준비할 자료:** 직접 사용 권한이 있는 짧은 MP4 영상 3개, 대표 이미지, 작품명·제작연도·소개, 카테고리, 공개할 언어. 국제 공유를 위해 한국어·영어 소개를 준비할 수 있다.

**개발에 필요한 것:**

- 화면: 영상 업로드 진행률, 작품 등록 폼, 갤러리, 작품 상세·영상 플레이어.
- DB 제안: `artworks(id, owner_id, title, description, category, year, visibility)`와 `media(id, artwork_id, file_key, mime_type, size_bytes, upload_status)`.
- 파일: 영상·대표 이미지 원본은 객체 저장소. DB에는 경로와 설명만 저장.
- 로그인: 작가만 등록·수정·삭제, 관람객은 공개 작품만 조회. 비공개 파일은 서버 권한 검사 후 제공.
- 서버: 업로드 토큰 발급과 소유권 검증, 실패 파일 정리. 화면에서 형식만 검사하는 것으로 끝내지 않는다.
- 확장: 영상 변환·자막·음악 합성에는 별도 처리 작업과 상태 관리가 필요. 작품 연결은 먼저 수동 태그로 시작하고 이후 검색·AI 보조 추가.

**만드는 순서:** 샘플 영상 재생 → 제목·분류 화면 → 로그인 → 직접 업로드·DB 연결 → 공개 링크 → 편집·다국어.

**완료 확인:** 업로드한 작품이 새로고침 후에도 남고 재생된다. 타인의 작품 수정이 거부되고 비공개 작품이 공개 목록에 나오지 않는다.

**강의 포인트:** DB와 파일 저장소의 차이, 큰 파일 직접 업로드, 공개 범위, 음악·작품 사용 권한, 저장과 편집의 차이.

## 5. 심현정 · 칼퇴도우미

**앱 목표:** 연간 업무와 제출 마감일을 한눈에 확인하고 반복 업무를 줄인다.

**첫 버전:** 일정 등록·수정·삭제, 월별 캘린더, 마감일 목록, 완료 표시. 알림은 우선 화면 안의 마감 표시로 시작한다.

**준비할 자료:** 실제 업무 대신 민감정보를 제거한 샘플 일정 10개, 업무 종류, 마감일, 반복 주기, 샘플 서식. 알림 시점과 개인용/팀용 여부를 결정한다.

**개발에 필요한 것:**

- 화면: 월별 캘린더, 일정 입력, 마감순 목록, 완료 체크.
- DB 제안: `tasks(id, owner_id, title, due_at, category, status, recurrence_rule)`; 알림 확장 시 `reminders(id, task_id, scheduled_at, sent_at, status)`.
- 로그인: 개인 일정은 소유자만 접근. 팀 공유를 추가하면 조직·역할·공유 권한 설계.
- 파일: 반복 서식과 업무 첨부파일은 비공개 저장소, DB에는 소유자와 파일 경로 기록.
- 알림: Cron 등의 예약 실행 + 이메일/푸시 서비스 + 전송 기록. 중복 실행에도 같은 알림이 여러 번 발송되지 않게 처리.
- 분석 확장: CSV·엑셀·PDF 형식별 추출, 크기 제한, 분할 처리, 요약 결과의 원문 근거. 대용량 자료는 한 번의 AI 요청에 모두 넣지 않는다.

**만드는 순서:** 샘플 일정 화면 → 로그인·DB 저장 → 완료 표시 → 반복 일정 → 알림 → 서식·자료 분석.

**완료 확인:** 월을 이동해도 일정이 유지되고 한국 시간 기준 마감이 정확히 표시된다. 다른 사용자의 일정은 볼 수 없다. 알림 확장 시 재실행해도 중복 발송되지 않는다.

**강의 포인트:** 날짜·시간대, CRUD, 사용자별 데이터, 예약 작업과 알림 서비스의 차이, 업무 자료의 외부 AI 전송 범위.

## 6. 이봄길민들레 · 뚱냥이 방지 사료 측정앱

**앱 목표:** 보호자가 고양이 정보와 사료 열량을 입력해 하루 급여량을 확인하고 기록한다.

**첫 버전:** 입력 폼과 계산 결과. 실제 권장량을 제공하기 전 계산식·적용 대상·예외를 수의 전문가와 검증한다. 수업 중 검증되지 않은 계산은 설명용 예제로 표시하며 임의의 감량 처방을 제공하지 않는다.

**준비할 자료:** 나이·현재 체중·중성화 여부·활동 상태, 사료의 표시 열량과 단위, 전문가가 확인한 계산 규칙·출처·버전. 목표 체중과 감량 계획은 전문가가 정한 값을 사용하는 흐름을 설계한다.

**개발에 필요한 것:**

- 화면: 체중·열량 입력, 단위 안내, 입력 오류, 계산 근거와 결과 표시.
- 계산 코드: 숫자·범위 검증, 열량 단위 통일, 반올림 규칙, 계산 규칙 버전 관리. 핵심 계산은 AI 생성 문장 대신 검증된 코드로 수행.
- DB: 계산만 하는 첫 버전에는 불필요. 기록 확장 시 `cats(id, owner_id, name, birth_date, neutered)`와 `feeding_logs(id, cat_id, recorded_at, weight_kg, food_id, amount_g, rule_version)`.
- 파일: 첫 버전에는 불필요. 이후 고양이 사진·사료 라벨 사진을 보관할 때 저장소 추가.
- 로그인: 단순 계산에는 선택 사항, 여러 기기에서 고양이 기록을 보려면 필요.
- 추천 확장: 제품별 열량·성분·자료 출처·갱신일 필요. 이미지에서 읽은 열량은 사용자가 확인한 뒤 계산에 사용.

**만드는 순서:** 입력·단위 화면 → 전문가 검증 규칙 연결 → 오류·예외 처리 → 기록 저장 → 체중 추이 → 자료 기반 제품 탐색.

**완료 확인:** 열량 0·음수·빈칸·잘못된 단위는 계산하지 않는다. 전문가가 제공한 테스트 사례와 계산 결과가 일치한다. 규칙을 적용할 수 없는 경우에는 확인이 필요함을 안내한다.

**강의 포인트:** DB 없이 시작하는 앱, 숫자와 단위, AI와 결정적 계산의 차이, 근거 있는 규칙 검증.

## 7. 전필우 · 파워포인트 끝판왕

**앱 목표:** 강연자가 발표 내용을 슬라이드 구성안으로 빠르게 정리한다.

**첫 버전:** 주제·청중·발표 시간·슬라이드 수·핵심 내용을 입력하면 슬라이드별 제목과 핵심 문장을 생성한다. 사용자는 수정하고 텍스트로 내려받는다. 구성안 생성과 실제 PPTX 생성은 별도 단계다.

**준비할 자료:** 샘플 강연 주제 3개, 대상 청중, 발표 시간, 선호 말투, 참고 텍스트, 원하는 템플릿의 글꼴·색상·레이아웃 규칙.

**개발에 필요한 것:**

- 화면: 입력 폼, 생성 상태, 슬라이드별 편집 카드, 재생성·다운로드.
- 서버·AI: 기존 NVIDIA 텍스트 모델 연결 구조를 활용 가능. 제목·본문 등 정해진 구조로 결과를 받고 필수 항목과 슬라이드 수를 검증.
- DB: 일회성 생성은 없어도 됨. 저장 확장 시 `presentations(id, owner_id, topic, audience, duration_minutes)`와 `slides(id, presentation_id, position, title, bullets, notes, version)`.
- 파일: 이미지와 완성 PPTX를 영구 보관할 때 저장소 사용. 작은 텍스트 다운로드는 브라우저에서 가능.
- 이미지 생성: 텍스트 모델과 별도 이미지 생성 서비스·비용·권한이 필요. 첫 버전은 사용자가 준비한 이미지로 시작 가능.
- PPTX 확장: 파일 생성 라이브러리와 템플릿 규칙, 한글 글꼴·줄바꿈·텍스트 넘침·PowerPoint 호환성 검증 필요.

**만드는 순서:** AI 구성안 → 편집·텍스트 다운로드 → 로그인·저장 → 템플릿 적용·PPTX 내보내기 → 이미지 생성.

**완료 확인:** 요청한 슬라이드 수와 필수 항목이 맞고 생성 결과를 수정할 수 있다. 생성 실패 시 입력이 유지된다. PPTX 단계에서는 실제 PowerPoint로 열어 잘림과 글꼴을 확인한다.

**강의 포인트:** 구조화된 AI 결과, 텍스트와 파일 생성의 차이, 템플릿, 생성물 검토, 호출 비용 제한.

## 8. 홍용훈 · 헬퍼라이터

**앱 목표:** 작가의 인물·설정·상황에 맞는 대화문을 제안하고 장편 설정을 유지한다.

**첫 버전:** 장르·인물 이름·성격·관계·상황·말투·길이를 입력하면 대화문 초안을 제안한다. 수정·다른 버전 생성·텍스트 다운로드를 지원한다.

**준비할 자료:** 직접 작성한 샘플 인물 2명, 인물 관계, 세계관 규칙, 장면 3개, 말투 예시, 피하고 싶은 표현. 분석에 쓸 원고는 사용 가능한 본인 자료부터 준비한다.

**개발에 필요한 것:**

- 화면: 작품·인물·상황 입력, 대화문 결과, 버전 비교·편집.
- 서버·AI: 필요한 인물 설정과 장면만 전달하고 결과를 초안으로 표시. 기존 챗봇의 역할 설명과 자료 전달 구조를 활용 가능.
- DB: `projects(id, owner_id, title, genre)`, `characters(id, project_id, name, traits, speech_style)`, `chapters(id, project_id, number, body, summary, version)`, `generations(id, project_id, input, output, created_at)`.
- 파일: 긴 원고의 원본 업로드·백업은 비공개 저장소에 보관. 편집 가능한 텍스트와 버전은 DB에 관리.
- 로그인: 미공개 원고·설정은 소유자만 조회·편집. 외부 AI로 전달할 자료 범위를 사용자에게 안내.
- 장편 기억 확장: 원고 분할 → 회차 요약 → 관련 인물·설정 검색 → 관련 자료를 프롬프트에 전달. 처음은 키워드와 회차 선택, 이후 필요할 때 임베딩·벡터 검색 추가.
- 설정 관리: AI가 만든 요약·새 설정은 작가가 확인해야 확정 설정으로 저장. 최근 대화만 보낸다고 장편 전체가 기억되는 것은 아님.

**만드는 순서:** 대화문 생성 → 편집·다른 버전 → 로그인·작품별 저장 → 인물·회차 관리 → 요약과 검색 기반 기억.

**완료 확인:** 인물과 말투 설정을 전달한 결과가 나오고 작가가 수정할 수 있다. 작품 간 설정이 섞이지 않고 타인의 원고가 검색되지 않는다. 이전 버전을 보존한다.

**강의 포인트:** 저장과 AI 기억의 차이, 컨텍스트 길이, 검색 후 생성, 원고 버전, 작가가 확정하는 설정.

## 9. 이새벽 · 던맵 (가제)

**앱 이름의 의미:** `DAWN`(새벽)과 `Done`(완료)의 두 의미를 담은 가제다.

**앱 목표:** 목표를 계획하고 실천하기 어려운 사람이 장기 목표를 작은 단계로 나누고, 가벼운 마음으로 꾸준히 기록하며 포기하지 않고 도달하도록 돕는다.

**첫 버전:** 목표를 등록하고 직접 하위 할 일을 추가해 완료 상태를 바꾸는 목표 보드. 목표별 진행률과 완료 기록을 보여준다. AI 추천과 게임 요소는 기본 저장·조회·수정 흐름이 안정된 다음 추가한다.

**준비할 자료:** 실제 목표 예시 3개, 목표별 하위 할 일 5~10개, 목표 기간과 완료 기준, 기록하고 싶은 성취 항목, 선호하는 게임 보상 방식. AI 추천 결과를 평가할 좋은 예시와 부적절한 예시도 준비한다.

**개발에 필요한 것:**

- 화면: 목표 목록·상세, 하위 할 일 추가와 완료 체크, 진행률, 과정 기록, 성취 모아보기.
- DB 제안: `goals(id, owner_id, title, description, starts_at, target_at, status)`와 `goal_tasks(id, goal_id, title, position, status, completed_at)`, `achievement_logs(id, goal_id, body, recorded_at)`.
- 로그인·동기화: 계정으로 로그인하고 모든 기록에 `owner_id`를 연결한다. PC와 휴대폰은 같은 서버 DB를 조회하며, 다른 사용자의 목표를 읽거나 수정할 수 없게 서버에서 소유권을 검사한다.
- AI: 목표 제목·설명·기간을 바탕으로 하위 할 일 후보와 분류를 구조화된 형식으로 제안한다. 사용자가 검토·수정하고 선택한 항목만 DB에 저장하며, 추천이 목표 달성을 보장한다고 표현하지 않는다.
- PDF: 성취 기록을 인쇄용 카드 화면으로 구성하고 PDF로 저장한다. 한글 글꼴, 줄바꿈, 여러 페이지, 날짜 표시를 실제 PC와 휴대폰에서 확인한다.
- 게이미피케이션: 완료 수에 따른 경험치·배지처럼 규칙을 코드로 명확히 정의한다. 기록을 조작하거나 목표를 삭제했을 때 점수를 어떻게 처리할지도 정한다.

**만드는 순서:** 목표 CRUD → 하위 할 일·진행률 → 로그인·기기 간 동기화 → 과정·성취 기록 → PDF 출력 → AI 추천·분류 → 경험치·배지.

**완료 확인:** 한 기기에서 만든 목표와 완료 기록이 같은 계정의 다른 기기에서 보이고, 다른 계정에서는 보이지 않는다. 목표별 진행률이 하위 할 일 완료 상태와 일치한다. PDF에 선택한 성취 기록이 카드 형태로 빠짐없이 저장된다. AI 제안은 사용자가 승인하기 전에는 할 일로 등록되지 않는다.

**강의 포인트:** 목표와 하위 할 일의 관계, 사용자별 CRUD와 동기화, 진행률 계산, 구조화된 AI 추천과 사용자 승인, 인쇄 화면과 PDF 파일의 차이.

## 11. 다음 수업에서 준비하고 결정할 것

1. 각 수강생이 첫 버전의 입력과 결과를 한 문장씩 적는다.
2. 실제 사용할 자료 3~10개를 준비한다. 공개 가능 여부와 출처도 기록한다.
3. 첫 화면을 종이에 그린다. 정상 결과·자료 없음·오류 상태를 함께 생각한다.
4. 저장이 필요한지, 파일 업로드가 필요한지, 로그인할 사용자가 누구인지 정한다.
5. 화면과 샘플 자료로 먼저 시연한 뒤 필요한 DB·저장소·AI만 연결한다.
6. Vercel 배포 후 새로고침·다른 기기·권한 거부·입력 오류·저장 실패를 확인한다.

강사는 공통으로 GitHub·Vercel 계정과 서버 환경변수 설정을 안내하고, DB가 필요한 팀에는 연습용 DB 연결과 기본 CRUD를 제공한다. 업로드 팀에는 파일 저장소와 권한 검사 예제, AI 팀에는 입력 검증·출력 형식·실패 처리가 포함된 서버 API 예제를 제공한다. 상용 운영 전에는 각 서비스의 요금제·이용 조건과 예상 비용을 다시 확인한다.

기술 설명은 작성일에 확인한 공식 자료를 참고했으며, 서비스 제한과 요금제는 실제 배포 시 다시 확인합니다.
